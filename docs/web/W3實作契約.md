**先 W3-B 規則，再 W3-A UI。** 字母沿總計畫保留，不代表施工順序。完成後可從正常開局讀完 D1 上午／下午、到站 evening 及第一夜，抵達 D2 morning；W4 在這裡接白天地圖。

開局已需要發卡、旗標與條件判定，因此 B 提早建立同一個 `cards.ts`／`effect.ts`／`condition.ts` 的最小正式子集，W4-A／W5 接著擴充。不在 UI、開局與測試各寫一份 gain 或 evaluator。為接通 W5 的前幾天可玩切片，前兩夜既有的免費 fixed 演出也先建立共用入口；W6 再擴充一般夜間地點，不跳過原內容。

W3／W4 的公開流程目前到 D2 morning 為止；尚不能做當日放卡。界線屬開發中可用範圍，不是新增玩法：未完成範圍的命令回 `not_implemented` 且零副作用，UI 不提供會假裝繼續的操作。W5 完成後把界線延至 D3 evening；W6-A 開始便以機制守衛取代日期界線，依該次命令真正需要的未完成機制拒絕，不再一律擋高日數。不得用 stub 夜晚一路假跑到 D45。

## 三、W3-B：共用狀態與最小流程

### 狀態、查詢與通知介面

`web/src/core/state-types.ts` 定義 `GameSnapshot`，外部形狀直接對應當前 Godot `serialize()` 的 `flow`／`run`／`meta`。所有已存在的參照欄位在初態就有正確空值，不因尚未移植而省略；chapter 由 day 導出，transient 演出文字、UI 選取與訂閱者不序列化。不是正式存檔讀取器，W7 才處理版本與不可信外部存檔。

```typescript
type MutationResult = {
  ok: boolean; reason_code: string; reason_text: string; lines: string[];
};
type AdvanceResult = MutationResult & { phase_advanced: boolean };

function createGame(data: GameData, initialState?: GameSnapshot): Game;
// Game 的 public API：
getSnapshot(): Readonly<GameSnapshot>;
serialize(): GameSnapshot;
subscribe(listener: () => void): () => void;
chapter(): number;
openingScreenView(): { title: string; prompt: string };
openingView(): readonly OpeningOptionView[];
chooseOpening(choiceId: string): MutationResult;
advancePhase(): AdvanceResult;
playBeat(beatId: string): MutationResult;
playEvening(): MutationResult;
playNightFixed(): MutationResult;
getPhaseView(): PhaseView;
```

`createGame(data)` 正常啟動在 opening，手牌空。`initialState` 僅給 Node 測試／走查注入可信的參照快照，深複製後使用同一個 production Game；正式 UI 不傳、不提供讀檔入口。不使用測試專用 Game 子類或重新實作規則。run／meta 精確欄位由本步根據 Godot serialize 定義，不在 W4／W5 另立平行狀態型別。

Node 走查的正式建構入口另定在 `web/src/core/trace-entry.ts`：

```typescript
function createRunForTrace(data: GameData): Game;
```

它與 `chooseOpening()` 共用 `web/src/core/run-initialization.ts` 的 `initializeRun(state: GameSnapshot, data: GameData): GameSnapshot`：在複本上清 run、建立主角卡、依資料恢復 persistent 物品、凍結開輪知識。初始化規則只有這一份；一般開局在此之後才套 on_select、寫開局 id 並執行 auto_enter。trace 入口從 `createGame(data).serialize()` 的正常 fresh 初態出發，meta 也不另手組；切 flow 為 run／active_ending 為 null，再呼叫相同初始化器，**不套開局選擇、不寫開局 id、不跑 D1 morning auto_enter**，與 Godot `start_fresh_run()` 同義。

共用初始化器產生的可信結果可交給 `createGame(data, initialState)` 建立正式 Game；這與讀 expected 的起點複製成 actual 不同。`createRunForTrace()` 不讀 Godot baseline，也不在 greedy helper 手組另一份 run 預設值。trace-entry 僅供 Node 腳本／測試 import；正式 main、UI 及其 barrel export 不得 import／re-export，瀏覽器 build 不包含這個入口。

`getSnapshot()` 返回只讀且在沒有更新時 identity 穩定的快照，供 React `useSyncExternalStore` 使用；`serialize()` 返回脫離即時狀態的深複本，不能把可變參照交給 trace。每次命令完成後才通知 UI，不能讓訂閱者看到效果套一半的狀態；拒絕不發佈新狀態。重播文字等 transient 顯示有變時也要通知，但不增加參照序列化欄位。

`OpeningOptionView` 包含來源的 id、label、preview、confirm_text、available、reason_text，不傳 requires、on_select 或 note。`PhaseView` 包含 day／phase／chapter、純演出標記、當前可呈現文字與可推進狀態；UI 不自己篩選 beat 或推算時段。

Game 持有當前時段的 transient 呈現文字，不加入 GameSnapshot／serialize。正式換時段時清除上一時段文字，以本次 `last_choice_default_lines` 初始化（無文字則為空），再按入場結算順序接入當前畫面應呈現的文字；初次開局同樣保存 auto_enter 文字。`getPhaseView()` 是純查詢，只讀暫存文字與當前狀態，絕不呼叫 `playBeat()`、`playEvening()` 或 `playNightFixed()`，不消耗或清空文字。

### 開局與效果最小子集

- 開局選項依資料順序；預覽／取消只改 UI，不能改序列化狀態。確認才呼叫 `chooseOpening()`。
- 拒絕順序沿來源：mode → id → unlock → 資料形狀；保留 `not_opening`、`unknown_opening_choice`、`opening_choice_locked`、`data_conflict`。
- 相簿與電話分別從正式 `on_select` 取效果，不按 choice id 寫死 gain／flag。初始化順序沿來源：重置 run → 主角卡 → 依 cards 順序恢復 meta 物品 → 凍結開輪知識 → on_select → 記開局 id → run mode → D1 morning auto_enter。
- `on_select` 預演若會提出 ending request，`chooseOpening()` 必須回 `data_conflict`，完整狀態不變；不得藉一般效果入口啟動結局。這與資料明示 `ending` 的「不上車」專用入口不同。
- `cards.ts` 先支援普通 unique 卡、slotless 知識分流、主角卡保留；W5-A 補齊卡片操作與 UI。這不是提早做備用區或遭遇。
- `condition.ts` 本步只需 `null`、`opening_choice`、`ending_seen` 的正式判定；函式簽名沿 [W4-A](W4實作契約.md#三w4-a完整條件求值器) 所定 `evalCondition(condition, state, data)`，W4-A 擴充同一入口為完整語彙。遇到尚未支援的運算子明確失敗，不能默認 true。
- `effect.ts` 本步只執行正式開局／初期固定演出實際用到的 `text`、`gain`、`flag`，沿固定鍵序，先在複本上算完再提交。介面以 [W5-B](W5實作契約.md#四w5-b交易放置預覽與行動格) 的 `EffectPlan`／`planEffects()` 為準，動工前只需額外讀該介面小節。遇到其他效果先拒絕整筆，不能套前半筆後忽略剩餘鍵。W5-B 擴充同一個交易入口，勿建立 `OpeningEffect` 的第二套解譯器。
- 首輪「不上車」按正式 requires 鎖定，理由原文顯示。解鎖後的 ending 流程屬 W6-E；本步不偽造歷輪結局、不提供假成功，注入已解鎖狀態時命令只能回 `not_implemented`，全狀態不變。

### 推進與演出生命週期

`facts.ts` 負責 next phase 的純結構計算；Game 負責可用範圍內的正式 transition。`advancePhase()` 成功換時段才 `phase_advanced:true`；mode 不對、階段界線或尚未可執行的機制，必須在 mutation 前擋下。章節邊界與 D45 無 night 的結構可用純函式測，不要求 W3 跑通 D45，更不建立假結局。

`advancePhase()` 從 W3 就保留以下七步骨架，後續只補步驟內容，不換檢查順序。表中的「無需執行」必須由當前狀態與當下成立資料判定，不能把尚未支援當成沒有內容：

| 順序 | 步驟 | W3 行為與後續接手 |
|---|---|---|
| 1 | mode gate | 已實作；非 run 回 `not_run` |
| 2 | active encounter gate | 已實作；有 active encounter 回 `encounter_active`，不需等 W6-D 才能擋 |
| 3 | night 睡覺解析與停拍 | 已選地點或已 sleep_pending 就不再解析睡覺；否則無旅館可播內容才繼續，有內容而解析未接則回 `not_implemented`。W6-A 接通後，有文字可成功停拍，回 `phase_advanced:false`；若進 ending 也不往後推進 |
| 4 | 逾期 choice default 的純預演 | 無當下待結算 default 就繼續；需要時、未接前回 `not_implemented`，由 W6-E2 接手。預演不得落地；接通後失敗回 `unresolved_choice_conflict` |
| 5 | phase_exit 門檻 | 無當下適用門檻就繼續；需要時、未接前回 `not_implemented`，由 W6-E2 接手。接通後未滿足回 `phase_requirements_incomplete`；D45 evening 不能因缺 ending 接點而放行到 night／D46 |
| 6 | 目標／結局與 due encounter 預檢 | 已實作結構目標及範圍檢查；需要 ending plan 或固定遭遇但尚未接上時回 `not_implemented`。結局底座由 W6-E1 接、coda 出口由 E2 接；遭遇由 W6-D 接。接通後壞引用／資料回 `data_conflict`，在換時段前擋下 |
| 7 | commit | 已實作可用切片；先提交已預演的 default，再 transition 或啟動 ending，依下表完成入場順序後通知 UI |

第 3 步成功停拍是已完成的命令，允許寫入睡覺內容及 pending，再直接 return；**不是拒絕零副作用的情況，也不繼續執行第 4～7 步**。W6 的機制守衛只檢查這次真的會走到的步驟。確定要進第 7 步時，下列入場動作若仍有必要機制未接，須在提交 default／換日／tick 前拒絕整筆，不能執行到一半才回未完成。

`_commit_phase_transition()` 對應的入場順序也固定：

| 順序 | 動作 | W3 行為與後續接手 |
|---|---|---|
| 1 | 清本次入場 transient，更新 day／phase | W3 已實作；保留本次 default 的結果文字，不把它清掉 |
| 2 | night → morning 時 tick 發狂錶、將本次歸零實例入列 | 時計空就無事可做；需要 tick 時未接回 `not_implemented`，W6-A 接手 |
| 3 | 套預扣行動、重設當格 action_spent；非行動時段清預扣 | 無預扣的正常重設由 W3 實作；有預扣的成本接線由 W6-B 接手，未接不能吞掉預扣 |
| 4 | 清當夜 chosen／sleep_pending | W3 已實作，每次正式換時段沿來源清理 |
| 5 | 行動時段第一個可用格結算 forced_pending | 空佇列無事可做；需要結算而未接回 `not_implemented`，W6-B 接手 |
| 6 | morning 依順序結算 pending 委託回報 | 無到期 report 就無事可做；有到期 report 而未接回 `not_implemented`，W6-C 接手 |
| 7 | morning 清今日已受託集合 | 空集合無事可做；非空集合的換日清理由 W6-C 接手 |
| 8 | 結算 auto_enter | W3 已接；仍用共用 playBeat／交易；所需效果未完成則整筆拒絕 |
| 9 | 若仍在 run，建立 due fixed encounter | 無適用遭遇就無事可做；需要而未接回 `not_implemented`，W6-D 接手；不能在入場效果已進 ending 後再建立遭遇 |
| 10 | 發佈完成狀態與 phase／chapter 更新 | W3 已接，訂閱者不看到半套入場狀態；chapter 仍由 day 導出 |

D45 afternoon → evening 沿來源的專用 transition 分支：不做換日 tick，先處理該分支的 transient／action_spent，再 auto_enter 與適用遭遇；evening 的結局出口在七步主流程內處理。不能硬套 night → morning 的全部工作。

`playBeat()` 取 authored text，每輪第一次才結算 on_enter，並與 beats_entered 一次提交；重看可重播正文，不重複效果。只有正式來源已有的 day-layer 地點記入 `meta.day_locations_visited`，不要把夜間或 unknown 地點填進去。這是所有管道共用的入口；後續 W5 的面板也走它。

開局與每次 transition 的 `auto_enter` 由規則層結算，D1 morning 不可漏接；玩家讀文字不再套第二次效果。evening 的 fixed beat 依資料順序走 `playBeat()`，再處理當日 echo；前兩夜的免費 fixed 依原 `playNightFixed()` 的 meta_once 與 forced visit 語意記錄 seen／chosen，再走同一入口。`night.ts` 只建立這段已需要的正式功能，W6 接著擴充。

UI controller 與 Node runner 都顯式呼叫上述演出命令；不要靠 React mount effect 才結算，也不把晚上正文只留在 UI。本次實際播出的 night-layer fixed 若已成功強制到訪，就不能額外做第二次手動到訪；meta_once 已看而跳過時不佔今晚名額。入夜到換日清理依上述順序；通用睡覺內容解析、收費夜間地圖與發狂機制留 W6。

兩端在每次進入 evening／night 時各顯式呼叫對應命令一次。`playEvening()`／`playNightFixed()` 依 Godot 的 beats_entered／meta_once 等守衛結算一次性效果，將此次產出文字存入 Game 的當前時段暫存並回傳 MutationResult；default 文字保留在正文之前。React 重繪只讀 `getPhaseView()`。若命令再次被顯式呼叫，仍沿來源的重播／seen 語意回傳，不重套一次性效果；同一時段已保存的首次演出正文（含 on_enter 文字）不被後續重播結果覆寫，重播文字不在暫存中重複累加，空結果也不得抹除先前正文，不把兩個命令一律改成第二次 no-op。

## 四、W3-A：開局與純演出 UI

### 接線與可動檔案

新增 `web/src/ui/use-game.ts`、`OpeningPanel.tsx`、`NarrationPanel.tsx`、`GameShell.tsx`、`strings.ts`、`styles.css`；修改 `App.tsx`、`main.tsx` 接 W2 loader 與 Game。載入成功才建 Game；資料載入失敗顯示技術錯誤且不進遊戲。

依 W-02 已定決策，UI 介面詞彙統一放在 `strings.ts`，沿用原 Godot UI 的既有文案並附來源檔／節點註記；不改 data、不自編劇情或替 locked 選項劇透。完整決策見 `待決事項.md` 第六節 W-02。

開局顯示 title／prompt、三選項與原鎖定理由；預覽→確認／取消。純演出時段不出地圖或卡槽，只顯示規則層產出的文字；每段由玩家明示繼續，不自動計時連播。此階段不做逐字動畫。切換 phase 不可把上一個命令的結果文字立刻沖掉。

字型沿總計畫選型；W3 自託管可用版本，W7-C 才子集化與容量優化。成品放 `web/public/fonts/lxgw-wenkai-tc.woff2`、`taipei-sans-tc.woff2`，授權原文各住同目錄對應子資料夾；worker 從正式來源核對實際授權後才能交付，不自行假設可改名或可轉授權。`font-display:swap`，不接字型 CDN。若需 Python 轉檔依 AGENTS 建專案 venv，工具中間檔不進 repo。

建立 `web/playwright.config.ts`、`web/tests/ui/opening.spec.ts`、`web/tests/ui/narration.spec.ts`，package 加 `test:ui`。使用 Playwright 專用 headless Chromium，不設定 Edge channel／executablePath；若自行 launch 要 finally close，使用 Playwright test fixture 則由 fixture teardown 關閉。Chromium 不可用或驗收失敗，停止瀏覽器驗收並報告。

## 五、Node 軌跡與交接

`npm run trace:web -- --output ../_qa/web/trace-web.json` 在 Node 讀正式資料，呼叫 `createRunForTrace(data)` 取得同一個 production Game。`greedy.ts` 只寫走法與 observer，不重算初始化或效果；**不選相簿／電話、不呼叫開局 auto_enter**，不能把正常開局的狀態拿來與另一種初始化的基線硬比。正式開局另由上節測試負責。

每夜先呼叫 `playNightFixed()`。只有確認**本次實際播出了掛在 night-layer 地點的 fixed beat，且強制到訪成功**，才斷言 night_location_chosen 等於該地點、meta seen 已記錄，並可在尚無一般查詢的階段省略「找可進地點」。實際執行依正式命令結果或本次前後狀態差異辨認，不以 day 是 1／2 或只看資料存在 fixed 推測。

meta_once 在後續輪次已看而跳過，或 fixed 掛在 day-layer 時，不能套用上述「今晚已佔用」前提；若這次仍需要一般夜間查詢而尚未接上，將走查判為未完成，不無條件跳過。W5 共用同一 helper。W6-A 接查詢後，實際已強制到訪時查不到第二個可進地點；未佔用時則真的按 Godot 的收費優先策略選地點。初輪前兩夜只是這條規則的現行例子。

W3 軌跡產生到 D1 night 的 `phase_end`，seq 0～4，共五筆，不產 opening／ending 的假 checkpoint。manifest／policy 與 W1 相同；W3 scope 明訂 `throughSeq:4`、`ignorePaths:[]`，這個已完成的小範圍完整比，不用忽略欄位遮住差異。前兩夜所需 subset 若仍未接齊，該步就是未完成，不能縮成只比 day／phase。
