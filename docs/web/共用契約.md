# 網頁版共用契約

本檔管網頁版各 W 階段共用的工程與派工規則。方向與階段表見 [網頁版移植計畫](網頁版移植計畫.md)，第一階段見 [W1 實作契約](W1實作契約.md)。遊戲規則仍引用根目錄既有文件，不在此重寫。

建立：2026-10-31。這是實作前契約，並非完成或驗收紀錄。

## 一、範圍與文件權責

- `data/` 是 Godot 與網頁版共用的內容與數值來源；移植不得自行改劇情、規則或補造內容。
- Godot 的 `scripts/`、`scenes/` 在移植工單中只讀。這是本次移植的修改邊界，不代表已決定取消原版人工驗收；W-06 仍待使用者拍板。
- Godot 測試保留。W1 可在 `tests/headless/` 新增產生器，並對既有走查加唯讀觀測接點；不得改走法、斷言或正式規則來配合網頁版。
- `web/prototype/` 是示意稿，`web/public/art/` 是既有素材。W1 不覆寫、不刪除、不把示意稿當成規則來源。
- 各 W 階段群各有一份實作契約，內含「驗收規格／實作設計／必要驗證」三種責任，不另複製三份遊戲規格書。開始下一階段前才補該階段契約。
- 實作者交付程式、測試與證據；指揮者審核整合；verifier 判定驗收、更新進度。實作者不得替自己勾完成。整體進度仍只住 `PROJECT_BRIEF.md`，本目錄不另建一套全案進度表。
- 網頁版待決 W-01～W-06 住 `待決事項.md` 第六節，不複製到本檔。工單只列當步真正受影響的項目。

## 二、架構與資料邊界

| 區域 | 責任 | 約束 |
|---|---|---|
| `web/src/core/` | 規則、狀態、效果與生命週期 | 純 TS；不得依賴 React、DOM、瀏覽器儲存或網路。Node 能獨立執行 |
| `web/src/data/` | JSON 型別與載入 | 瀏覽器載入與 Node 讀檔各自處理 I/O，共用內容型別；不把 I/O 藏進規則函式 |
| `web/src/ui/` | React 顯示與輸入 | 呼叫規則入口，讀結果與狀態；不得另算一次玩法效果 |
| `web/scripts/` | 資料同步及開發工具入口 | 專案根目錄 `data/` → `web/public/data/`，單向產生 |
| `tools/trace/` | 引擎無關的軌跡格式與比對器 | 不 import React 或遊戲狀態實作，可在 Node CLI 執行 |

規則層收到已載入資料後才建立狀態；不得在 import 時自動讀檔、建立全域遊戲或啟動 UI。訂閱用於通知 UI 更新，正式狀態仍由規則入口修改；訂閱 API 的簽名由首次需要它的 W 階段契約定義，不在 W1 先建空抽象。

Godot API 與 schema 是行為參照，不要求逐字保留命名；對外簽名、回傳值、狀態所有權須在各階段動工前寫定。不得由兩個 worker 各自猜同一個介面。

資料列與陣列保持來源順序；物件鍵排序只用於差分，不得排序後再交給依序挑選的遊戲規則。`web/public/data/` 是產物，不接受手動修正、不提交；開發啟動及正式 build 前都重新同步，刪掉來源檔也不得留下舊產物。lint 清單以開工時 `scripts/autoload/data.gd` 實際接線為準，不照抄總計畫早期的條數。

## 三、快速檢查：以命令列為主

**網頁版不能依賴人工點網頁驗玩法。** 原 Godot headless 的工作由 Node 接手；瀏覽器只驗畫面與輸入接線。

下列命令均在 `web/` 執行，是逐階段實作後必須提供的固定入口：

| 命令 | 用途 | 何時具備 |
|---|---|---|
| `npm ci` | 從提交的 lockfile 安裝依賴 | W1-A |
| `npm test` | 非 watch 的必要自動測試；W1 先驗資料同步，W1-C 再納入比對器 | W1-A 起逐步增加 |
| `npm run build` | 資料同步 → TS 型別檢查 → Vite 靜態建置，任一步失敗即非零退出 | W1-A |
| `npm run trace:compare -- <expected> <actual>` | Node CLI 比對兩份軌跡 | W1-C |
| `npm run trace:web -- --output <path>` | Node 執行已移植規則及既定走法，產生網頁版軌跡 | 首次具備可對帳規則的階段；W1 不做假 runner |
| `npm run test:ui` | Playwright 必要 UI 自動驗證 | W3 首次玩家畫面起 |

W2 的 build 加入資料 lint。日常改動先跑相關測試及 build；規則改動再跑當階段的 Node 軌跡與對帳。45 天全程 runner 於 W6 規則齊備後接通，W7-A 收斂全程對帳。Node runner 與 UI 必須使用同一份 production 規則，不另寫測試版遊戲。

測試不能把「沒有測試」「沒有 checkpoint」或「零欄位被比較」算成成功。尚未具備的命令應在交接中明列，不建永遠 exit 0 的占位命令。

## 四、必要驗證的取捨

驗證以能攔住當步真實錯誤為準：

1. 建置與型別檢查：所有程式工單皆須通過。
2. 規則測試：正式資料的主要流程、該次修改涉及的關鍵拒絕與副作用契約。既有 Godot 案例能直接定位時優先沿用案例意圖，不逐行翻譯整套測試。
3. 軌跡：證明既定走法上已移植範圍一致；單條貪心路徑不代表所有分支都驗過。
4. UI：只測當階段新增的玩家入口、結果顯示及會阻斷流程的接線。規則細節交給 Node，不用瀏覽器重跑每個規則排列。

不預先堆砌巨量壞資料、任意深度物件、極端數量或窮舉組合；除非正式資料、已知問題或明確契約需要。關鍵規則仍遵守 `AGENTS.md` 的變異保真要求，只選能證明該接線的最小改動與對應測試，不展開全系統突變矩陣。

瀏覽器自動驗證只用 Playwright 專用 Chromium／Chrome Headless Shell：`chromium.launch({ headless: true })`，並在 `finally` 關閉。禁止 Edge；專用 Chromium 不可用或驗收失敗時停止該瀏覽器驗收並報告，不影響獨立執行 Node 測試。W1 空殼只需啟動服務確認 HTML 與資料 HTTP 可讀，不先建瀏覽器測試框架。

## 五、差分範圍與基線管理

- `GameState.serialize()` 的 `flow`、`run`、`meta` 完整輸出作 Godot 參照快照，不自行挑掉看似無用的狀態。網頁版可用不同內部結構，但對帳時須輸出相同的參照形狀；這不決定正式存檔相容性（W-05）。
- 比較 JSON 值；物件鍵順序不算差異，陣列順序、缺鍵與 `null` 均算差異。不對數字做容差、不刪玩家文字、不排序集合狀陣列來掩蓋差異。
- 每個階段工單明列 checkpoint 範圍與未移植欄位的精確路徑。不得忽略整個 `run`／`meta` 等父區塊來取得綠燈；選定範圍至少比較一個實際狀態欄位。W7-A 忽略清單為空。
- 資料 manifest 與走法版本不同時先報基線不適用，不把它當成玩法差分。來源 revision 用於追溯，不要求 Godot 與 web 的提交 hash 相同。
- 重產基線是獨立、明示操作；一般測試不得覆寫 expected。更新基線須附原因、來源 revision、資料 manifest 與走查結果；不能拿 TS 的結果反寫 Godot expected。
- W1 只建立 Godot 基線及比對器，不宣稱 Godot／TS 玩法已一致。開局、其他分支、UI 可達性由後續對應契約驗證，不能用這條軌跡代替。

## 六、指揮與交接

指揮者沿用 [指揮者手冊](../others/conductor-handbook.md) 的角色、監看、審 diff 與交接流程；該手冊已改為 ReturnFare 路徑與規則。網頁版各步的確切命令、驗證範圍與契約入口以本檔及當階段契約補充：`npm test` 已是非 watch，不必再加 `--run`；W1-B 僅加走查觀測接點，按 W1 契約跑相關 Godot 入口，不因此擴大成每步全套回歸。外部工具操作按 [local-tools.md](../others/local-tools.md) 對應段落讀取；repo 外的 prompt 範本仍須按手冊換成本專案內容。

每次派工至少指定：

- W 子階段與目標，工作目錄、branch、開工前 HEAD，以及前置成果是否已審核。
- 本檔、該階段契約對應小節、要動的最新程式與 API；背景規則只定位相關章節。
- 逐檔修改白名單、不得動的區域、依賴及共用檔案的唯一負責人。
- 本步完成條件、確切測試命令、預期結果及回報證據。
- git 操作權限依使用者授權與 worker 類型明列；本契約本身不授權 commit、push 或部署。

worker 回報檔案、新增／修改的 API、命令與 exit code、軌跡路徑與比較範圍，以及未完成事項。指揮者讀 diff、核對範圍，執行本步必要 gate；失敗時退回原 worker 修正，不以口頭成功代替證據。

實作紀錄的位置與格式沿用指揮者手冊 §2.4，住 `docs/records/`，不另在 `docs/web/` 維護第二份步驟板。W1 以 `docs/records/W1實作紀錄.md` 一張板列 A／B／C，詳細步驟住 `docs/records/W1_steps/`；由指揮者在派工時建立，本次只立契約，不先填虛構成果。原有 `CODEX_HANDOFF.md` 的 verifier 歷史區塊保留，網頁版接手時指向相關契約與紀錄即可。
