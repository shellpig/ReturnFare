# W5 能玩實作契約

建立：2026-10-31。實作前契約；先讀 [共用契約](共用契約.md)、[W3](W3實作契約.md) 的狀態 API、[W4](W4實作契約.md) 的 VM 與演出流程。

## 一、交付範圍與依賴

順序 W5-A 手牌 → W5-B 放卡與效果 → W5-C 互斥選擇。共用 `state.ts`、`cards.ts`、`effect.ts`、panel／UI，原則上順序派工；沒有先固定介面與獨占檔案，不讓多 worker 同時改 Game。

完成後從正常開局可玩到 D3 evening：D2／D3 白天選地點、演出、主角卡行動、免費比對；前兩晚的 fixed 內容與 seen 已由 W3 共用入口接好，不略過夜晚。一般夜間收費、發狂時鐘、縱慾、委託、遭遇與結局仍屬 W6；W5 期間 D3 evening 之後的推進明確停在開發界線，不能無聲跳過這些規則。W6-A 開始以機制守衛取代日期界線，不阻擋已接好的高日數生命週期測試。

`choice_group` 在正式早期可玩切片尚無足夠案例，C 用正式 D22／D43 資料及可信狀態驗證；不為了展示新增假事件或改寫原劇情。完整 45 天可玩與全程軌跡不是 W5 驗收。

## 三、W5-A：卡片、手牌與知識

### 共用 API 與規則

擴充 W3 的 `cards.ts` 與 Game，不另寫開局卡片容器。規則層提供：

```typescript
hasCard(cardId: string): boolean;
hasKnowledge(cardId: string): boolean;
handSlotsUsed(): number;
cardView(instanceId: string): CardView;
handView(): readonly CardView[];
knowledgeView(): readonly CardView[];
```

`CardView` 提供 instanceId、baseId、type、name、text、必要的倒數顯示；正文只來自 cards。用 instanceId 作 React key，不能把不同發狂實例都當同一張卡。

普通卡 unique，重複 gain 不增加張數；slotless 卡只進 meta.knowledge；主角卡持續在手牌釘死位，不能 lose，放進槽不代表移出手牌。知識順序沿目前集合的取得順序，不為畫面美觀排序後污染 trace。容量從 tuning 讀，超載照收卡並可查詢，不做備用區／整理 UI。

卡片變更 helper 只作規則內部使用：gain 按卡定義分流，lose 對指定實例／知識生效；loop_persistent、permanent 語意沿既有來源，不能順手改成日常丟棄功能。發狂多實例可在本步補齊 id／初始時計資料結構，W6 才接倒數、cap 與清除玩法；W5 玩家操作不得藉 gain madness 繞過尚未有的 cap／BE。

### UI、白名單與必要驗證

- 新增 `web/src/ui/HandPanel.tsx`、`CardDetail.tsx`、`web/tests/cards.test.ts`、`web/tests/ui/hand.spec.ts`。
- 修改 `cards.ts`、`state.ts`、`state-types.ts`、GameShell／styles／strings；既有開局仍用同一套 gain。
- 手牌與知識分開，顯示卡名與佔格數／上限；點卡看原文詳情，關閉零副作用。不要求沿 Godot 七欄格線，只要標準桌面畫面可讀且不溢出。
- Node 驗普通卡冪等、知識不佔格、主角卡不能移除、兩個發狂實例不混同；不測大量卡片或極端容量。代表性操作後序列化維持參照形狀。
- UI 一條正常相簿開局確認主角與相簿各一張、詳情可關；知識顯示用正式知識卡的可信狀態作補充，不假稱相簿開局已取得知識。`npm test`／`build` 與必要 UI 測試通過。

## 四、W5-B：交易、放置、預覽與行動格

### 效果交易介面

W3 已建立的 `effect.ts` 沿用並補齊本階段效果；由此處定義共用介面，W3 的最小子集也依同一形狀實作：

```typescript
type EffectPlan =
  | { ok: true; nextState: GameSnapshot; lines: string[];
      endingRequest: { ending_id: string; source_id: string } | null }
  | { ok: false; reason_code: string; reason_text: string; lines: string[] };
function planEffects(
  blocks: readonly (Effect | null | undefined)[],
  state: GameSnapshot,
  data: GameData,
): EffectPlan;
```

在 detached draft 上依固定順序 `text → lose → gain → switch → switch_progress → relation → madness → flag → festival_proxy → ending` 求值。每張條件 gain／lose 讀「當時已套完前序效果」的 draft，不把所有 if 先對舊狀態算一次。文字只在成功時對外發佈；失敗不能回傳彷彿已發生的前半段結果。

W5 執行 text／lose／gain／switch／switch_progress／relation／flag，含條件卡片項目與永久 lose 的現行語意；`madness`、`festival_proxy`、`ending` 的玩法執行留 W6。資料型別及 lint 知道這些鍵，但若此次真的需要執行未完成機制，整筆回 `not_implemented`，真狀態及文字零變化；包含 gain 陣列直接給 madness 的繞路。不得忽略鍵後回成功。

Game 的共用 settle 流程在 draft 上合併效果與 bookkeeping，全部可提交才一次換入狀態、發通知。bookkeeping 的前／後順序沿 `_settle_effects()`；選擇、on_enter、放卡都走同一入口。TS 可直接提交已驗完的 draft，不必為了模仿 Godot 再建立第二套逐 op 重播器；禁止先套 live 再靠失敗 rollback。

### 放置 API 與判斷

```typescript
tryPlace(cardId: string, beatId: string, slotId: string): MutationResult;
placeableCards(beatId: string, slotId: string): readonly string[];
previewSlot(beatId: string, slotId: string): { cards: readonly string[]; reason: string };
hasAnyLegalAction(): boolean;
hasUnseenContent(): boolean;
```

`tryPlace()` 的 `cardId` 是持有集合 `hand ∪ knowledge` 內的項目 id，即卡片實例 id。普通 unique 卡與知識卡的 instanceId 等於 baseId；發狂卡則必須傳 `madness#N`，不能傳裸 `madness` 代替指定的一張。候選／預覽返回同一種實例 id，UI 提交原值；只有查卡片定義、type／accepts 匹配或明定的 base 去重時才取 baseId。`choose()` 的可選 cardId 與 W6 的 `indulge()` 沿用此語意。

沿現行 GameState 先驗 mode／遭遇守衛，再解析卡／beat／slot 與路由。一般放卡共用 checkPlace：持有 → 時間與三態／一次性 → accepts → 主角卡 action_spent。type 或 base card id 擇一匹配 accepts，`[]` 永遠不可放。preview、候選與提交使用同一判斷；未持有的 registry 卡不能通過。

主角卡在行動時段成功才消耗當格，不移走主角卡、不自動跳時段；免費比對不吃格。寫入 `slots_placed[beat_id::slot_id]`，同槽不可重複；`attention_npc` 只在實際消耗主角行動成功時增加一次。effect、slot、投入帳與 action_spent 同一筆提交，拒絕時 serialize 逐字不變。

`tryPlace()` 遇 choice 由 W5-C 接 `choose()`；C 整合前回未完成，不能先當普通槽結算。madness／delegation 槽在 W6 才有正式路由，本步零副作用拒絕，不把人物委託當普通免費放卡。

W4 的 `playBeat()` 現在使用補齊後的 effect pipeline，所有 on_enter／on_place 同源；UI 逐一演出與每次重求值沿 W4，不改成開面板就全部結算。前兩夜的 meta_once 固定演出沿 W3，Game 的可推進界線延至 D3 evening。

## 五、W5-C：choice_group

### API 與語意

```typescript
choose(beatId: string, groupId: string, slotId: string, cardId?: string): MutationResult;
```

新增 `web/src/core/choice.ts` 存本功能必要的共用判斷，或留在現有 state／placement 內；以不重複 checkPlace／settle 為準，不為一個函式硬拆檔。兩個入口共用 choose：玩家直接選，或 tryPlace 導入帶卡選。

檢查依最新來源：mode／active encounter → 該組未結算 → beat／slot 且屬該 group → 未完成的專用路由守衛 → choice_requires_card → slot state → 有帶卡時共用 checkPlace → effect 與 bookkeeping 原子提交。group key 含 beat id。拒絕回與來源一致的 code；重複選擇回 `resolved`，不套第二次效果。

普通 choice 的 accepts 只約束帶卡入口；無卡直選同樣結算同一個 on_place。兩條路除了明示卡片效果／成本，留下相同狀態；`choice_requires_card:true` 才禁止無卡，提交 protagonist 且在行動格才消耗行動並記 attention。不得把所有帶主角卡的普通 choice 一律算成有成本。

同時記 choices 與 slots_placed；被選項保留 RESOLVED，其他同組選項消失。玩家關面板未選不寫任何選擇；`default_if_unresolved` 的離開時段結算、D29 慶典代付與一般 phase_exit 在 W6 接完整生命週期，本步不能在關面板時提早套 default。後續階段遇到這些未接機制必須整筆拒絕，不靜默略過。

### UI 與必要驗證

- 修改 state／placement／panel／effect、LocationPanel／SlotView；新增 `web/tests/choice.test.ts`、`web/tests/ui/choice.spec.ts`。
- Node 用正式 `d22_pm_sandbags` 的 observation choice，從相同可信快照各跑直選與帶 `equip_polaroid` 選 `obs_walk`，比較完整 serialize 相同；fixture 只補足該正式案例需要的持有狀態，不改 beat／slot。再測關面板未選不改狀態與重複選擇不重套。

## 六、軌跡、派工收尾與 W6 邊界

W5 的 Node greedy runner 使用 W3 的 `createRunForTrace(data)`，從共用正式初始化器產生與 W1 相同的 helper 初態；處理每個行動時段、evening 及前兩夜 fixed 後取樣，不跳過中間夜晚、不把 expected 的快照複製進 actual。前兩夜若尚未呼叫夜間地點查詢，必須先通過 W3 所定的 chosen／seen 斷言；不另寫無條件略過夜間查詢的分支。

`tools/trace/scopes/W5.json` 為 `throughSeq:11`、`ignorePaths:[]`：run_start 加 D1／D2 四時段及 D3 morning／afternoon／evening，共十二筆。正常開局的額外相簿／電話狀態不混入這條參照走法。W5-C 高日數案例獨立測，D1～D3 軌跡不宣稱涵蓋 choice。

每步收尾跑 focused Node 測試、現有 `npm test`／`build`，有 UI 改動才跑對應 Playwright；W5 全部整合後跑一次當前必要 UI 集及十二筆軌跡對帳，不每回合反覆全套 Godot。所有實際命令、exit code、比較筆數、最小變異證據與未完成路由，記 `docs/records/W5實作紀錄.md`／`W5_steps/`。

交 W6 時列清：一般夜間與睡覺解析、madness 倒數／cap、縱慾、委託、遭遇、ending／重置、逾期 choice default／phase_exit，哪些仍回 not_implemented。W6-A 先移除日期守衛並改為依機制判斷；各機制守衛待對應子階段接好後移除。這與 Node trace 的十二筆截止不同，trace 到 E2 才擴成全程；未完成不得用空回傳或白名單對帳冒充全程可玩。
