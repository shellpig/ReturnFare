# W4 地圖與面板實作契約

建立：2026-10-31。實作前契約；先讀 [共用契約](共用契約.md)、[W3](W3實作契約.md)。前置為 W3-B 的 Game／開局／初期演出及 W3-A UI 已整合。

## 一、交付範圍與順序

W4-A 將 W3 已建立的條件入口補齊為完整求值器；W4-B 接白天地圖、面板與三態。順序 A → B。完成後正常開局可抵達 D2 morning，點地點讀演出與簡介，查看槽及理由；**仍不能放卡或選 choice**。可用流程界線沿 W3，W5 才接動作。

「唯讀」指槽目前無提交操作，不是省略正式 `on_enter`。演出仍由 W3 的 `playBeat()` 結算其已支援效果；`buildPanel()`／地圖查詢則始終零副作用。高日數的 view-model 測試可注入可信參照快照，但不能用這些測試宣稱玩家已可一路玩到該日。

## 三、W4-A：完整條件求值器

### 介面與語意

擴充既有 `web/src/core/condition.ts`，保留單一入口：

```typescript
function evalCondition(
  condition: Condition | null | undefined,
  state: GameSnapshot,
  data: GameData,
): boolean;
```

純查詢、不讀全域 Game、不改狀態。語彙取 W2 `vocabulary.ts`，與 build lint 相同；W3 的子集在這裡完整化，不另建 evaluator。涵蓋來源現行的 `day`、`day_at_least`、`has_card`、`has_knowledge`、`switch`、`switch_progress_at_least`、`flag`、`relation_at_least`、`madness_at_least`、`night_seen`、`opening_choice`、`ending_seen`、`festival_proxy_is`、`count_at_least`、`not`、`all`、`any`。

缺條件為 true；`all:[]` 為 true、`any:[]` 為 false；count 與巢狀邏輯沿來源。has_card 是 hand ∪ knowledge，不從 registry 存在推導成持有；關係門檻查 `relation_scale.json`，未持有狀態依原函式的預設值判斷。madness 門檻沿現行 evaluator 計 `madness_clock` 的實例數，W6 負責讓手牌與錶保持一致；不在這裡順便改 Godot 規則。

型別外的未知鍵通常已被 W2 擋住；直接誤用 evaluator 時也不得當 true，明確回報開發錯誤。不要新增容忍任意物件的 fallback 分支來吞掉資料問題。

### 可動檔案與必要驗證

- 修改 `web/src/core/condition.ts`、必要的 `cards.ts` 共用持有查詢；若 W2 型別確實漏欄可補 `data/types.ts`／`vocabulary.ts`，不改來源 JSON。
- 新增 `web/tests/condition.test.ts`。同一張參數表為每個正式運算子提供必要的真／假例，不為每個運算子另建測試檔；另測一個符合正式資料用法的巢狀組合。
- 以正式卡片與關係表驗「registry 有但沒持有」不算 has_card；呼叫前後 serialize 相同。選一個會影響正式面板的 requires 判斷反轉，確認對應測試紅，再還原。
- `npm test`、`npm run build`，加跑 W3 的既有正式開局測試，不重跑 Godot 全套。

## 四、W4-B：白天地圖與面板

### 規則層 view model

在 `web/src/core/panel.ts` 定義並匯出 `MapLocationView`、`PanelView`、`BeatView`、`SlotView`，由 Game 提供以下查詢，全部不改 serialize：

```typescript
availableLocations(): readonly string[];
mapView(): readonly MapLocationView[];
buildPanel(locationId: string): PanelView;
remainingActionsToday(): number;
```

`availableLocations()` 先依 day／both layer、chapter、phases 篩選，順序沿來源；純演出時段回空。一般夜間清單屬 W6，不回傳一份假完成的白天清單。

`MapLocationView` 包含 id、name、enabled，以及有資料時的 map 座標；不得帶 beat 標題、內容摘要或未揭露 note。enabled 依 T-03：目前有非 HIDDEN beat，或該地點已在 meta.day_locations_visited，才可按；無內容且未到訪的地點保留灰色按鈕。查詢不順便寫到訪。若已到訪的空地點可開，只顯示正式 desc，不自編空場景事件。

`PanelView` 含 location 的 id／name／desc 及有序 `BeatView[]`；beat 帶 id／title／text／tri／reason／slots。slot 帶 id／label／occupant 的顯示資料、tri／reason、isChoice、acceptTypes，供後續 W5 擴充預覽及操作。UI 只讀 VM，不自行判斷原始 condition、requires、accepts 或資料層 note。

三態用固定值 `HIDDEN=0`、`LOCKED=1`、`OPEN=2`，另有 `RESOLVED=3` 表示已結算；不是第四種可操作狀態。求值與來源一致：

1. 取當下 location／when 候選，condition 不成立整個 beat 不進公開 VM。
2. beat requires 不成立，顯示 LOCKED 與來源理由，將未結算的內部槽降為 LOCKED；已結算者保留 RESOLVED。
3. slot 先處理已結算 choice 的組內選項，再依 condition、已放置、requires 求值；通過後若 `indulgence.soak:true`，還要比較 `remainingActionsToday()` 與 `tuning.indulgence.soak_phase_cost`，不足則 LOCKED。理由沿 Godot：非 morning 為「（只能在上午發動）」，morning 為「（格數不足）」；足夠才 OPEN。beat LOCKED 的降級與理由覆蓋仍依第 2 點，RESOLVED 不重判泡湯成本。HIDDEN 不建立玩家控制項。
4. 一般已放置槽可留於內部 VM 作 RESOLVED，但 UI 收起；choice 已選項保留 RESOLVED、同組其他項收起。key 均為 `beat_id::slot_id`／`beat_id::group_id`。

`remainingActionsToday()` 是規則層純查詢：morning 為當格未用的數量，加上 afternoon 尚未被 actions_spent_ahead 預扣的數量；afternoon 只看當格是否未用，其餘時段為 0。按 `remaining_actions_today()` 移植，不能只看 phase 就假定 morning 一定還有完整行動格。泡湯成本讀 tuning，不寫死數值。

上述兩句原始碼理由收進既有純字串 `web/src/ui/strings.ts`，註明來源為 `panel_builder.gd` 的 soak 分支，供規則層引用；此模組不 import React／DOM。成本判斷與理由選擇仍在 core，不交 UI 重算，也不為此修改 data。

本步只讀既有 choices／slots_placed，不建立選擇命令。委託、縱慾等未完成機制不接提交，但**既有玩法的三態判斷（含 soak）仍須完整移植**；不因未實作而假鎖，也不因未開放提交而略過真正的 LOCKED 條件。開發階段的未實作狀態與玩法 LOCKED 分開。

acceptTypes 將具體 card id 反查 type，再查 card_types 的名稱，去重且保序，用「、」串接。不能把指定卡名當答案貼在槽上。occupant 保留 authored label；`accepts:[]` 的展示槽無提交操作。

### UI 接線

新增 `web/src/ui/MapPanel.tsx`、`LocationPanel.tsx`、`SlotView.tsx`。GameShell 接 mapView 與選定地點，所有槽在 W4 均無提交按鈕。地圖先用可驗證的地點清單；既有 map／scene 素材可在 data id 對應的地點直接顯示，但不修改座標、重畫地圖或做新美術。沒有圖的地點用文字版面，不臨時造圖；W4 不以像素座標校準作驗收。

進地點立即播放第一個可呈現 beat，呼叫 production `playBeat()`；後續 beat 由玩家按一下才播下一個。每播完一個重建 panel，依來源順序找下一個仍成立的未播 beat；本次面板的播放游標住 UI，不另寫進 run。不要在開面板時把全部 on_enter 一口氣結算。

演出期間**不建立卡槽控制項**，全部演完才顯示 desc、occupant 與槽。重開地點正文仍可重播，效果一次性由規則層保證。React 重繪不能自動再播下一段。關面板只改 UI；目前狀態變化後重求值，不以每幀輪詢更新。

### 可動檔案與必要驗證

- 新增 `web/src/core/panel.ts`、`web/tests/panel.test.ts`、`web/tests/ui/map-panel.spec.ts`。
- 修改 `state.ts` 接上述查詢、`state-types.ts` 必要型別、GameShell／NarrationPanel／styles／strings 與既有 Playwright 設定。不得建立第二份 loader／Game 或修改 Godot、data、素材檔。
- Node 正式資料取 D3 afternoon 的三個地點，核對各自 beat 與槽順序；用可信快照驗一組 HIDDEN／LOCKED／OPEN、beat requires 傳導及指定卡 id 只露型別名。fixture 可從 W1 基線取已有狀態後明列必要差異，不偽造 beat 代替正式內容。
- 同一案例多次 mapView／buildPanel 前後 serialize 逐字相同；已到訪空點可開、未到訪空點灰掉。playBeat 後才寫到訪，stage／過濾查詢不能偷偷寫入。
- 正式 `exit_sanquan.x_soak` 用同一個持有發狂卡的可信快照，分別驗 morning 行動足夠時 OPEN、morning 已耗／預扣而不足時 LOCKED「（格數不足）」、afternoon 不足時 LOCKED「（只能在上午發動）」；查詢不改狀態。只驗成本分支，不在 W4 提早做泡湯提交或新增極端資料。
- 一條正常 UI 路徑：從 opening 玩到 D2 morning → 開山泉閣第一段立即出現 → 讀完才出槽 → 返回地圖再開，正文可重看。另確認灰色未到訪空點不能進入。不在瀏覽器窮舉所有地點。
- 最小變異移除 slot condition 過濾或 beat LOCKED 傳導其中之一，對應 Node 測試必紅；原接線還原後通過。`npm test`、`npm run build`、必要 `test:ui` 通過。

## 五、軌跡與交接

W4 增加的是查詢與演出 UI，尚未接放卡；W3 的五筆前綴對帳仍須全欄位一致，不為了「看起來有進展」增加無法執行的 checkpoint 或擴大 ignore。

完整條件／高日數面板由本步 Node 測試負責，不用 D1 軌跡宣稱已覆蓋。留 `docs/records/W4實作紀錄.md`／`W4_steps/`，交 W5 時附 VM 型別、panel 播放接線、唯讀證據與尚未接的 action／preview。verifier 才能判定 W4；W5 不得再換一套 map／panel 規則。
