建議按 A → B → C 派工，避免共用檔衝突。不預設需要多 agent 同時寫。若指揮者選擇讓 A、B 並行，A 獨占 `web/` 與 `.gitignore`，B 獨占走查與基線檔；先確認本檔格式，C 等兩者審核後再接。

## 二、W1-A：網頁骨架與資料同步

### 驗收規格

- `web/` 可用 `npm ci`、`npm test`、`npm run build` 與 `npm run dev`。
- build 先同步資料及檢查 TS，再產出 `web/dist/`；dev 啟動前同步資料。
- 開發頁可載入空殼，`/data/tuning.json` 與 `/art/map/town.webp` 可經 HTTP 存取。空殼只作技術入口，不把示意稿改成正式遊戲。
- 複製的是根目錄 `data/` 下全部 `.json`（包含 `beats/`），保持相對路徑與檔案內容。不同步 `SCHEMA.md`；不在此重寫 schema 或實作資料 lint。

### 實作設計與可動檔案

W1-A 可新增：

```text
web/package.json
web/package-lock.json
web/index.html
web/tsconfig.json
web/tsconfig.node.json          # 僅工具鏈確有需要時建立
web/vite.config.ts
web/src/main.tsx
web/src/ui/App.tsx
web/scripts/sync-data.mjs
web/tests/sync-data.test.ts
```

可修改根目錄 `.gitignore`，僅加入 `/web/node_modules/`、`/web/dist/`、`/web/public/data/` 及本步實際產生的 TS build cache（若有）。不得整段重寫既有 ignore。

沿用總計畫的 React 18／Vite／TS，確切版本由本步安裝後 lockfile 固定；使用目前本機 Node 24 工具鏈。Vitest 以 `vitest run` 執行，非 watch，沒有測試時不得 pass。不要建立 root npm workspace 或第二個 `tools/trace/package.json`。

`sync-data.mjs` 匯出 `syncData(sourceDir, targetDir)` 供測試，CLI 的來源／目的以腳本位置解析，不能依賴啟動者 cwd。只重建指定的產物目錄 `web/public/data/`，不得清空 `public/` 或觸碰 `art/`；刪除前核對解析後的目標確為該產物目錄。測試只傳入本案例建立的暫存來源／目的，不對正式 `data/` 注入壞資料。

`package.json` 由 A 建立 `dev`、`build`、`test`；W1-C 才加入 `trace:compare`。`build` 須包含 TS 型別檢查，不能只呼叫 Vite 當作 TS 已驗過。程式尚未需要的 `core/`、loader、訂閱系統不先放假實作。

### 必要驗證

1. `sync-data.test.ts` 用一組含子目錄的暫存 JSON 驗證內容相同，來源刪檔後重新同步，目的舊檔消失；相鄰的素材檔仍保留。這一個案例涵蓋本步實際同步責任，不另做大量路徑攻擊案例。
2. `npm ci`、`npm test`、`npm run build` 均 exit 0；將根目錄與產物的 JSON 相對路徑及內容逐檔核對一致。
3. 短暫啟動 `npm run dev -- --host 127.0.0.1`，用 HTTP 讀空殼、上述 JSON 與素材成功，結束後關閉本次服務。W1 不要求人工點擊或 Playwright。

## 三、W1-B：Godot 黃金軌跡

### 必讀與實際入口

- `tests/headless/playthrough_greedy.gd`：完整讀取；核對 `run_greedy_walk()`、四種時段 helper、結局迴圈及工廠。
- `scripts/autoload/game_state.gd`：定位 `serialize()`、`advance_phase()`、`reveal_ending_page()`、`advance_ending_page()`、`complete_ending()`；只讀相關函式。
- `scripts/autoload/data.gd`：載入及 lint 接線；`project.godot` 的 autoload。
- 根目錄三份 Phase 文件定位 P1-F、P5-D；規則／既有操作驗收按章節引用，不把舊 stub 描述當最新 API。必要時沿 stub 指向的歸檔讀取。

目前真實介面為 `run_greedy_walk(gs: Node, data_node: Node, verbose: bool = false) -> Dictionary`。`setup_game_state()` 會呼叫 `start_fresh_run()`，借 `_apply_run_initialization` 起一輪，**不走正式 `choose_opening()`**。B 沿用此既有走法，不為了基線改選開局；正式開局由 W3 自己驗證。

### 軌跡格式 v1

產物為 UTF-8 JSON；頂層如下。型別是契約描述，不要求先建立 TS 遊戲狀態型別：

```typescript
type Trace = {
  schema_version: 1;
  policy: 'greedy-v1';
  source_revision: string;
  data_manifest: Array<{ path: string; sha256: string }>;
  checkpoints: Array<{
    seq: number;
    label: string;
    day: number;
    phase: 'morning' | 'afternoon' | 'evening' | 'night';
    state: { flow: object; run: object; meta: object };
  }>;
};
```

- `source_revision` 由啟動命令傳入當前 `git rev-parse HEAD`；指揮者另確認相關來源及資料無未提交變動。W1 新增的測試觀測接點可尚未提交，須在實作紀錄附 diff／檔案清單，不謊稱整份產生器已在該 revision。
- manifest 遞迴列出根目錄 `data/` 下全部 `.json`，`path` 使用相對 `data/` 的 `/` 路徑，依 path 排序，SHA-256 取檔案原始 bytes；不含 schema 文件。Godot 可用 `FileAccess.get_sha256()`。
- `seq` 從 0 連續遞增；每筆 `state` 都是當時 `serialize()` 的深複本。不可只保存可變 Dictionary 的引用，也不可剔除任何序列化欄位。
- `day`／`phase` 記取樣當時狀態；`label` 標示觀測位置，不能只用 day／phase 當唯一 key（結局翻頁時時段不變）。
- 不記生成時間、絕對路徑、process id 等每次不同的值；確保同來源能重現。

### 取樣位置與接點

對既有走查增加唯一可選參數，既有三參數呼叫保持原行為：

```gdscript
static func run_greedy_walk(gs: Node, data_node: Node, verbose: bool = false, observer: Callable = Callable()) -> Dictionary:
```

observer 有效時，按 `observer.call(label, gs)` 同步呼叫；observer 只讀，不改規則狀態。未提供 observer 時不產檔、不額外呼叫規則。

| label | 時點 |
|---|---|
| `run_start` | 既有初始化完成，第一天上午行動前 |
| `phase_end` | 每個時段 helper 結束、推進時段之前；night 在 `execute_night_phase()` 後、`advance_until_phase_changes()` 前 |
| `ending_started` | 第 45 天 evening 的推進已啟動 ending、既有逐頁結算迴圈開始前 |
| `ending_step` | 結局迴圈每次 reveal 或 advance 呼叫後；不含 complete |
| `opening_ready` | `complete_ending()` 成功回到 opening 後 |

預期 `phase_end` 共 **179 筆**：第 1～44 天各四時段，第 45 天上午／下午／傍晚，沒有第 45 夜。另有起點與結局觀測；總筆數依正式結局頁數決定，不硬寫總數。這是時段邊界快照，不是每次放卡或夜間停拍的操作 log；其間差異若在邊界前消失，本軌跡不宣稱能抓到。後續有重要契約才加針對性測試，不在 W1 建全操作攔截器。

### 可動檔案與產物

```text

tests/headless/generate_greedy_trace.gd    # 新增 SceneTree runner
tests/headless/generate_greedy_trace.gd.uid # Godot 自動產生時一併交付
```

產生器 await 初始 frame，沿用既有 `setup_data()`、`setup_game_state()`、`run_greedy_walk()`。輸出參數缺少、走查失敗、取樣不完整或寫檔失敗均非零退出；失敗不得覆蓋原基線。不要改 Godot 正式程式來加入 trace 功能。

從 repo 根目錄執行的預定 CLI：

```powershell
$traceRevisionW1 = git rev-parse HEAD
& 'C:\_work\Godot_v4.6.3\Godot_v4.6.3-stable_win64_console.exe' --headless --path . --script res://tests/headless/generate_greedy_trace.gd -- --output _qa/web/trace-godot.json --source-revision $traceRevisionW1
```

`--output` 相對路徑以專案根目錄解析；可接絕對路徑。建立所需父目錄，JSON 與日誌分開，stdout 不灌整份快照。一般驗證輸出到已 ignore 的 `_qa/web/`；指揮者檢查後才明示將合格結果放入 `tools/trace/baselines/greedy-godot.json`，一般測試不得自動更新它。新增 GDScript 後首次 headless 前先 `--import`；本機已有 log 權限限制，沿用可用的執行環境，不先故意跑一次會 crash 的受限環境。

### 必要驗證

1. 原 `playthrough_greedy.gd` 與 `test_p1f.gd` 各 exit 0，確認加觀測未破壞既有呼叫與走法；無其他變更時不重跑全套 Godot 測試。
2. 相同 revision、資料與參數跑兩次產生器，完整 JSON 語意相等；每筆快照有 `flow`／`run`／`meta`，179 個時段位置齊全，結局與 opening 收尾都有記到，首筆不被最後狀態覆蓋。
3. 觀測開關兩次走查的既有結果與最終 `serialize()` 相同，可由產生器在驗證模式或一個 focused 測試完成；不對所有內部 helper 各加測試。
4. 基線不含正式開局的限制明列於交付；不拿此軌跡替 W3 的開局驗收打勾。

## 四、W1-C：Node 軌跡比對器

### 驗收規格與介面

比對器讀第三節格式；先確認 schema、policy、manifest 相同，再核對所選 checkpoint 的身份與 state。`source_revision` 只列於報告，不因兩端提交不同判失敗。

核心放 `tools/trace/compare.ts`，匯出 `compareTraces(expected, actual, options)` 回傳 `{ equal, comparedCheckpoints, comparedFields, difference }`。`difference` 為 `null` 或首個差異的 `{ seq, label, day, phase, path, expected, actual }`；缺鍵用明確的 missing 標示，不混同 `null`。先只做首個差異，不建 HTML 報表或列盡所有差分。

`options` 支援：

- `throughSeq`：包含該序號的前綴範圍，不提供則比全份；兩邊都必須具備該前綴，不能取較短長度就算成功。
- `ignorePaths`：相對 `state` 的精確 JSON Pointer 路徑陣列，預設空。不支援 glob、正則或動態規則；拒絕根與 `/flow`、`/run`、`/meta` 整區忽略。不存在的路徑報設定錯誤，不能默默忽略拼錯字。

前綴以外的 checkpoint 在分段對帳可尚未產生；前綴內 `seq`／`label`／`day`／`phase` 須相同。全量模式筆數必須相同。物件逐鍵、陣列逐 index 比較，遵守共用契約；`comparedFields` 計未被忽略的實際狀態葉值，為零不通過。

CLI 可同檔提供入口或新增薄入口 `tools/trace/cli.ts`，不要寫第二份比較演算法。由 `web/package.json` 的 `trace:compare` 用 `tsx` 執行，依賴仍只裝在 `web/`。

```powershell
# cwd: web/
npm run trace:compare -- ../tools/trace/baselines/greedy-godot.json ../_qa/web/trace-godot.json
npm run trace:compare -- ../tools/trace/baselines/greedy-godot.json ../_qa/web/trace-web.json --scope ../tools/trace/scopes/W3.json
```

`--scope` 讀 `{ "throughSeq": N, "ignorePaths": [...] }`。W1 不建立虛構的 W3 scope 或 trace-web；範例只定 CLI，後續階段明列 N 與欄位後才建該檔。

退出碼：0＝相同；1＝軌跡內容、checkpoint 或基線身份不一致；2＝讀檔、JSON／格式或 scope 設定錯誤。console 只輸出比較數量與首個差異，例如 `seq=42 day=11 phase=afternoon path=/run/action_spent expected=true actual=false`，不輸出整份狀態。

### 可動檔案

```text
tools/trace/compare.ts
tools/trace/cli.ts                  # 只有拆薄入口時需要
web/tests/trace.test.ts
web/package.json
web/package-lock.json
web/tsconfig.node.json              # 現有 TS 設定需納入工具檔時
web/tsconfig.json                   # 同上，僅必要範圍
```

W1-C 不修改基線來取得通過；工具檔也須被 TS 型別檢查涵蓋，不能只靠 tsx 執行。測試加入 A 的 `npm test`，不另裝一份工具依賴。

### 必要驗證

| 案例 | 應證明什麼 |
|---|---|
| 真實基線對自身／B 第二次輸出 | exit 0，實際比較到完整 checkpoints 與非零欄位 |
| 深複本只改一個已有的布林欄位 | exit 1，準確報 seq、day、phase 與欄位；expected 原檔不變 |
| 小型 fixture 調換物件鍵順序；交換陣列順序 | 前者相同，後者有差異；避免錯誤正規化 |
| 同一小型 fixture 增刪鍵／改成 null／少一筆 checkpoint | 各有差異，不把未比較的部分當成功 |
| 前綴＋一條 ignore path | 指定差異可排除，但其他欄位差異仍被抓到；零 checkpoint／全區忽略／拼錯 path 不通過 |
| 一份不同 manifest 與一份不可解析 JSON | 前者報基線不適用，後者 exit 2，不冒充相同 |

以上是工具本身會直接影響對帳可信度的必要案例；不加巨大 JSON、極端遞迴或亂數模糊測試。欄位反轉案例即本步最小變異證據，不再展開多輪突變。

## 五、指揮者收尾與交接

每步派工附該步白名單與 gate，不把整個 W1 一次丟給 worker 自行拆。worker 不動本檔、共用契約、總計畫、根目錄規格／進度文件，不自行勾驗收；指揮者依手冊格式記錄 `docs/records/W1實作紀錄.md` 及 `docs/records/W1_steps/`。

W1 收尾只需彙整並核對：

1. `web/` 的 `npm test`、`npm run build`，及 A 的 HTTP smoke 結果。
2. B 的兩個既有 Godot 入口、觀測開關等價、兩次產生結果、179 個時段與結局收尾證據。
3. C 對真實基線成功、對單欄位反轉失敗的 CLI exit code 與具體差異。
4. `git diff --check` 與改動清單符合白名單；沒有改正式規則、data、既有素材或驗收狀態。

verifier 依上述證據判定 W1，才更新整體進度。尚未做的 W2 loader／lint、W3 正式開局、Node 遊戲軌跡與 UI 自動測試留在交接，不以 W1 已完成暗示它們可用。本契約撰寫完成不等於 W1 關門，也不觸發 Phase 文件關門的自動 commit／push 流程。
